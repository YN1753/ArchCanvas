# Stage 1：自然语言 → ER DSL

## 目标

用户描述业务需求，Agent 输出合法的数据库设计。

例如：

> 做一个校园二手交易平台，用户可以发布商品、收藏商品、购买商品，商品支持多张图片。

输出：

```text
users
products
product_images
favorites
orders
```

以及它们的字段和关系。

## 1. Agent 职责

Agent 负责：

- 理解需求
- 提取实体
- 提取字段
- 推断关系
- 提出约束
- 发现歧义

Agent 不负责：

- React Flow JSON
- 节点坐标
- 最终 Go 文件

## 2. 流程

```text
User Requirement
 ↓
Requirement Extraction
 ↓
Entity / Relation Analysis
 ↓
Schema Proposal
 ↓
Structured Output
 ↓
DSL Validation
 ↓
修正或保存
```

## 3. Structured Output

定义明确 Go 类型：

```go
type ERDesign struct {
    Tables    []Table    `json:"tables"`
    Relations []Relation `json:"relations"`
}
```

模型输出后必须经过 validation。

## 4. Prompt 要求

必须明确：

- 不虚构需求
- 不随意增加业务模块
- 关系必须有依据
- 不确定的信息标记 assumption
- 严格符合 DSL
- 不输出业务代码

## 5. 数据库策略

提前确定：

- 主键类型
- 时间字段
- 删除策略
- 命名规范
- 默认索引策略
- nullable 策略

不要让模型每次自由决定这些基础规则。

## 6. 歧义处理

例如：

> 用户可以买商品。

可能设计成：

```text
orders.product_id
```

也可能需要：

```text
orders
order_items
products
```

Agent 可以输出：

```json
{
  "assumptions": [
    "当前按一个订单购买一个商品处理"
  ]
}
```

然后等待用户确认。

## 7. Tool

第一版只需要：

```text
get_current_schema
validate_schema
apply_schema
```

不要一开始做几十个 Tool。

## 8. Evaluation

建立 20~50 个需求测试集，测试：

- 实体识别
- 字段识别
- 一对多
- 多对多
- 唯一约束
- 多图片
- 状态字段
- 边界情况

指标：

```text
Schema Valid Rate
Requirement Coverage
Hallucination Rate
Human Correction Rate
```

## 9. 验收

用户输入自然语言：

```text
需求
 ↓
Agent
 ↓
合法 ER DSL
```

并能继续：

> “商品增加分类。”

Agent 必须基于已有 DSL 修改。
